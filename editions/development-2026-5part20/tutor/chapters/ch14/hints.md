# 14장. 기획한 챗봇을 내 주식서비스에 구현합니다 — 단계별 힌트

한 번에 한 단계만 전달합니다.

## H22-TOOL · 공시만 물어도 가격까지 조회합니다.

### 힌트 1
질문에 필요한 자료와 실제 실행 기록을 비교해보세요.

### 힌트 2
모델의 호출 제안과 서버에서 실행한 조회를 나눠 봅니다.

### 힌트 3
공시 질문은 종목 확인·공시 조회, 일반 개념은 조회 없음인지 서버 실행 기록에서 대조합니다.

### 명시적으로 정답을 요청했을 때
도구 설명과 서버 실행 조건을 확인하고 불필요한 조회 원인을 고칩니다. 모델의 선언은 실행 근거가 아닙니다.

## H22-STOCK · 후보 선택 후 질문이나 대상을 잊습니다.

### 힌트 1
선택 전 보관한 질문과 현재 대상을 확인해보세요.

### 힌트 2
화면의 상세 종목과 챗봇의 현재 대화 대상을 구분합니다.

### 힌트 3
후보 선택값을 실제 검색 결과와 서버에서 대조하고 원래 질문을 이어가는지 봅니다.

### 명시적으로 정답을 요청했을 때
이전 대상 근거와 최근 문맥은 지우되 새 전환 질문은 유지합니다. 늦은 응답은 새 대화에 붙이지 않습니다.

## H22-PERIOD · 3개월을 물었는데 자료 부족으로 나옵니다.

### 힌트 1
요청 기간과 실제 거래일을 나눠 확인해보세요.

### 힌트 2
최근 확인 가격 기준일에서 서울 날짜의 달력 3개월을 계산했는지 봅니다.

### 힌트 3
달력상의 기간을 고정 거래일 수로 바꾸어 계산하고 있지 않은지 확인합니다.

### 명시적으로 정답을 요청했을 때
월말 처리와 실제 첫/마지막 거래일을 표시하고 짧은 기간에 맞는 자료 부족 판정을 사용합니다.

## H22-LIMIT · 한도에 걸려 답변이 멈춥니다.

### 힌트 1
반복 호출인지 필요한 조회인지 먼저 확인해보세요.

### 힌트 2
동일 요청의 재사용과 후보 선택 뒤 새 요청 사용량을 구분합니다.

### 힌트 3
모델·조회·시간 상한과 요청 실패 상태를 확인합니다.

### 명시적으로 정답을 요청했을 때
상한을 무작정 늘리지 말고 실제 호출 흐름과 중복 원인을 확인합니다. 요청당 제한과 실제 검사 기록을 구분합니다.


신판 계약의 완료에는 신판 실제 근거가 필요합니다. 구판 실행 결과를 자동 승계하지 않습니다.
